# IPTV backend

Мини-бэкенд IPTV/OTT на Go и PostgreSQL: REST API выдаёт каталог доступных
по подписке ТВ-каналов и HLS URL выбранного канала. Оба ресурса защищены HTTP Basic Auth.
Схема и demo-данные создаются автоматически. Требования: [исходное ТЗ](docs/assignment.md).

## Запуск

Нужны Docker Engine, Docker Compose с командой `docker compose` и свободный
порт `8080`; для примеров API — curl. Команды ниже выполняются из корня проекта
в shell Linux/WSL. В чистом окружении один раз подготовьте настройки и запустите сервис:

```sh
cp .env.example .env
docker compose up
```

Для локального demo без создания `.env` достаточно одной команды:

```sh
docker compose --env-file .env.example up
```

В этом варианте добавляйте `--env-file .env.example` и к командам
`stop`, `down` и `up --build` ниже. Вариант с `.env` удобен для собственных настроек.

Compose собирает приложение и запускает его после готовности PostgreSQL 17.
Go на хосте не требуется. HTTP по умолчанию доступен по
`http://127.0.0.1:8080`; порт БД на хост не публикуется. После сборки и
инициализации дождитесь лога `HTTP server started`; запросы выполняйте во втором терминале.

```sh
docker compose stop
docker compose up
```

Данные БД сохраняются в named volume `postgres_data`, в том числе после
`docker compose down`. После изменения исходников пересоберите образ:

```sh
docker compose up --build
```

Compose берёт настройки из `.env` или окружения процесса; окружение имеет
приоритет. `.env.example` содержит публичные значения для локального demo
и отдельной тестовой БД. Локальный `.env` исключён из Git и Docker build context.

### Настройки

| Переменная | Назначение / значение по умолчанию |
| --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Обязательные параметры demo-БД в Compose |
| `DATABASE_URL` | Обязательный PostgreSQL DSN приложения |
| `HTTP_PORT` | Порт на хосте в Compose, `8080` |
| `HTTP_ADDR` | Адрес Go-процесса, `:8080`; Compose задаёт его явно |
| `DB_MAX_CONNS` | Максимум соединений pool, `10`, положительный `int32` |
| `LOG_LEVEL` | `debug`, `info`, `warn`, `error`; по умолчанию `info` |

В `DATABASE_URL` укажите те же пользователя, пароль и БД; hostname внутри
Compose — `db`, порт — `5432`. В URL экранируйте спецсимволы в логине
и пароле через percent-encoding. Стенд предназначен для локального запуска;
HTTP опубликован только на loopback, TLS внутри Docker-сети нет.

`POSTGRES_*` применяются при инициализации пустой БД: правка `.env` не меняет
пользователей и пароли в существующем volume. Go-приложение само `.env`
не читает; при запуске вне Compose передайте доступный `DATABASE_URL`
через окружение процесса.

### Инициализация и остановка

До открытия HTTP-порта приложение проверяет соединение с БД и выполняет
embedded SQL-миграции в порядке имён: создаёт `users`, `channels`, `subscriptions`,
`schema_migrations`, `data_seeds`. Схема и версии фиксируются одной транзакцией.
Seed отдельной транзакцией создаёт двух пользователей, пять каналов (четыре
активны, пятый выключен) и отметку `base_demo`, затем demo-подписки с отдельной
отметкой `subscriptions_demo`. Данные и обе отметки фиксируются вместе.
Каждый этап ограничен 3 секундами;
сбой откатывает его изменения и останавливает запуск.

Повторный запуск пропускает применённые миграции и завершённый seed, сохраняя
пользовательские изменения и удаления. Обновления схемы добавляют новой
миграцией, уже применённые SQL-файлы не редактируют.

Подписка хранится на пару пользователь–канал: `active` и nullable `expires_at`
типа `timestamptz`; `NULL` означает бессрочную подписку. Удаление пользователя
или канала удаляет связанные подписки. На чистой БД у `viewer` подписки на
каналы 1 и 5 бессрочные, на 2 — на сутки с первого seed, на 3 — выключена,
на 4 — уже истекла. Повторный запуск не продлевает срок и не восстанавливает
удалённые подписки. При обновлении прежней БД seed подписок выполняется отдельно
от уже завершённого `base_demo`: используются только сохранившиеся `viewer`
и demo-каналы с исходными номером и URL; существующие подписки не перезаписываются.

Оба ресурса учитывают подписки аутентифицированного пользователя. Доступ даёт
включённая подписка без срока либо с `expires_at` строго позже времени начала
SQL-запроса в БД. Равенство сроку означает истечение; фоновая задача не нужна.
Каталог включает только доступные активные каналы; playback активного канала
без действующей подписки возвращает `403`, выключенного или отсутствующего — `404`.

Публичные demo-учётные данные для локальной проверки:

| Логин | Пароль | Активен |
| --- | --- | --- |
| `viewer` | `viewer_demo` | да |
| `inactive` | `inactive_demo` | нет |

В БД сохраняются bcrypt-хэши с cost 10 и случайной солью. Пароли длиннее
72 байт UTF-8 отклоняются при хэшировании и проверке без усечения.
HLS URL имеют вид `https://stream.example.com/live/ch1/index.m3u8`;
потоковый сервер не предоставляется.

Образ собирается в два этапа: Go 1.26 компилирует статический бинарник,
а runtime `scratch` содержит бинарник и CA-сертификаты. Приложение работает
без root; exec `ENTRYPOINT` передаёт SIGTERM непосредственно процессу.
По SIGTERM приложение прекращает приём новых соединений и даёт текущим
HTTP-запросам до 10 секунд на завершение. При истечении срока отменяет их
context и закрывает соединения, затем закрывает pool БД. Compose ждёт до 15 секунд.
HTTP timeouts: headers — 5 с, read/write — 10 с, idle — 60 с.
Логи идут в stderr как JSON через `log/slog`; credentials и SQL-ошибки не выводятся.

## Каталог каналов

```sh
curl -u viewer:viewer_demo http://127.0.0.1:8080/api/v1/channels
```

`GET /api/v1/channels` возвращает `200` и `Content-Type: application/json`.
Ответ на чистой demo-БД в первые сутки после seed подписок:

```json
{"channels":[{"id":1,"number":1,"name":"Первый"},{"id":2,"number":2,"name":"Россия 1"}]}
```

В списке только активные каналы с действующей подпиской пользователя,
упорядоченные по `number`, затем `id`; пустой каталог —
`{"channels":[]}`. URL потоков в каталог не входят.

После истечения временной подписки канал 2 исчезает из demo-каталога.
Каталоги пользователей зависят от их подписок. SQL-операции ограничены
3 секундами каждая и учитывают отмену HTTP-запроса.

## Playback

```sh
curl -u viewer:viewer_demo http://127.0.0.1:8080/api/v1/channels/1/playback
```

`GET /api/v1/channels/{id}/playback` возвращает `200` и `Content-Type: application/json`:

```json
{"channel_id":1,"url":"https://stream.example.com/live/ch1/index.m3u8"}
```

URL берётся из `stream_url` активного канала в БД; потоковый сервер не нужен.
Доступ защищён тем же Basic Auth и подпиской, что и каталог. Канал и право
на просмотр читаются одним SQL-запросом; при отказе URL не возвращается.

ID разбирается через `strconv.ParseInt` как положительный десятичный `int64`
(от 1 до 9223372036854775807); ведущие нули и `+` допустимы.

## Ошибки и HTTP-контракт

Ошибки API имеют `Content-Type: application/json` и единый формат:

```json
{"error":{"code":"unauthorized","message":"authentication required"}}
```

| Статус | `error.code` | `error.message` / причина |
| --- | --- | --- |
| `401` | `unauthorized` | `authentication required`: отсутствующие/неверные credentials, неизвестный или неактивный пользователь; `WWW-Authenticate: Basic realm="iptv"` |
| `400` | `invalid_id` | `channel id must be a positive int64`: неверное число, ноль, отрицательное значение, переполнение |
| `403` | `subscription_required` | `active subscription required`: активный канал без подписки, с выключенной или истёкшей подпиской |
| `404` | `channel_not_found` | `channel not found`: несуществующий или выключенный канал |
| `404` | `not_found` | `resource not found`: неизвестный путь |
| `405` | `method_not_allowed` | `method not allowed`: неверный метод известного ресурса; `Allow: GET, HEAD` |
| `500` | `internal_error` | `internal server error`: внутренний сбой, включая недоступность БД; без внутренних подробностей |

Примеры отказов; `-i` показывает также статус и заголовки:

```sh
curl -i http://127.0.0.1:8080/api/v1/channels
curl -i -u inactive:inactive_demo http://127.0.0.1:8080/api/v1/channels
curl -i -u viewer:viewer_demo http://127.0.0.1:8080/api/v1/channels/abc/playback
curl -i -u viewer:viewer_demo http://127.0.0.1:8080/api/v1/channels/3/playback
curl -i -u viewer:viewer_demo http://127.0.0.1:8080/api/v1/channels/5/playback
```

Ожидаемые статусы по порядку: `401`, `401`, `400`, `403` (подписка на канал 3
выключена), `404` (канал 5 выключен). Заголовок `WWW-Authenticate` есть только у `401`.

Оба ресурса поддерживают `HEAD`: статус и заголовки соответствуют `GET`, тело
не передаётся. В `/api/v1` и `/api/v1/…` Basic Auth проверяется до канонизации
пути, выбора маршрута, метода и разбора ID. После успешной Auth неверный
метод известного ресурса даёт `405`, неизвестный путь — `404`, включая лишний
завершающий `/`. `ServeMux` перенаправляет пути с повторными `/` и сегментами
`.`/`..` на канонический URL после Auth. Единый JSON относится к прикладным
ошибкам; ошибки разбора HTTP до handler формирует `net/http`.

## Проверки

Для команд Makefile нужны Go 1.26+ и GNU Make в Linux или WSL:

```sh
make check
docker compose config --quiet
```

`make check` проверяет форматирование, build, vet и unit-тесты.
`make test` запускает только unit-тесты. Обе команды автономны:
Docker и PostgreSQL им не нужны. Все targets описаны в `make help`.

GitHub Actions запускает `make check` и `make integration` отдельными jobs
для PR в `main` и при `push` в `main`, в том числе после merge. Push в остальные
ветки и теги отдельно CI не запускает; новые коммиты открытого PR проверяются
через `pull_request`. Проверка после merge подтверждает итоговое состояние `main`.
Новый запуск отменяет устаревший прогон того же PR или `main`; каждый job
ограничен 10 минутами.

Integration-job поднимает PostgreSQL 17 через `compose.test.yaml` и останавливает
стенд шагом с `if: always()`. Go берётся из `go.mod`, кэш — через `actions/setup-go`,
публичные test-настройки — из `.env.example`.

В настройках GitHub ruleset `protect-main` требует PR, успешные checks `check`
и `integration`, актуальность ветки относительно `main` и разрешение обсуждений
перед merge. Прямой push, force push и удаление `main` запрещены, в том числе
для администратора. Approval другого участника не обязателен.

Integration-тесты проверяют SQL, миграции/seed, HTTP + PostgreSQL, отмену
запросов и возврат соединений. Нужны Docker и свободный порт `15432`.
Отдельная PostgreSQL 17 хранит данные в tmpfs, без demo-volume.
Пример использует публичные test-настройки, как CI:

```sh
docker compose --env-file .env.example -f compose.test.yaml -p iptv-test up -d --wait db
(
  . ./.env.example
  export TEST_DATABASE_URL
  make integration
)
docker compose --env-file .env.example -f compose.test.yaml -p iptv-test down
```

Настройки test-стенда задаются переменными `TEST_POSTGRES_USER`,
`TEST_POSTGRES_PASSWORD`, `TEST_POSTGRES_DB`, `TEST_POSTGRES_PORT`
и `TEST_DATABASE_URL`. Для собственных настроек замените `.env.example` на
подготовленный `.env` в командах выше. Пользователь, пароль, имя БД и порт
в `TEST_DATABASE_URL` должны соответствовать test-стенду. Файл примера
совместим с shell; значения со спецсимволами заключайте в одинарные кавычки.
Если настройки уже экспортированы в окружение, запускайте `make integration`
напрямую, без загрузки `.env` в shell.

Остановите test-стенд и при ошибке тестов. `TEST_DATABASE_URL` обязателен,
отсутствие — ошибка; используйте только отдельную test-БД. Каждый тест
создаёт свою schema, задаёт `search_path` всем соединениям и удаляет её после закрытия pool.

## Структура и решения

| Путь | Ответственность |
| --- | --- |
| `cmd/server/` | Сборка компонентов, HTTP-сервер и lifecycle |
| `internal/config/`, `internal/auth/` | Переменные окружения, bcrypt |
| `internal/httpapi/` | Basic Auth, маршруты, handlers, JSON |
| `internal/iptv/` | Модели, каталог и playback, предметные ошибки |
| `internal/postgres/` | Pool, параметризованный SQL, embedded-миграции и seed |
| `internal/testdb/` | Изолированные схемы для integration-тестов |

PostgreSQL выбран для транзакций миграций/seed и явных SQL-запросов;
цена — отдельный сервис БД в окружении. HTTP-слой зависит от узких интерфейсов
потребителей; PostgreSQL не знает про HTTP. Компоненты связываются явно
в `main`, без ORM и DI-контейнера.
Auth передаёт только user ID через request context; handlers передают его
явным аргументом в сценарии. Фильтрация, сортировка и проверка срока выполняются
в SQL; сценарий playback запрещает выдачу URL без права.
Параметры `$1` отделяют пользовательские данные от SQL; отсутствие строки
отличается от сбоя БД. JSON содержит только поля публичного контракта.

Внешняя зависимость `github.com/jackc/pgx/v5/pgxpool` предоставляет PostgreSQL
драйвер и pool соединений. `golang.org/x/crypto/bcrypt` нужен для безопасного
хэширования и проверки паролей, которых нет в stdlib. Остальной код использует
stdlib. Транзитивные модули `pgpassfile`, `pgservicefile`, `puddle/v2`,
`x/sync`, `x/text` обеспечивают работу pgx/pool; версии закреплены в `go.mod` и `go.sum`.

## Ограничения и возможные улучшения

Реализованы бессрочные и временные подписки на отдельные каналы. Администрирование
и кэширование отсутствуют. Нет CRUD API, пагинации и проверки доступности видеопотока.
`stream_url` возвращается из БД без дополнительной валидации и подписания;
demo-ссылки — примеры HLS URL.

Basic Auth защищает выдачу URL, а не сам поток. Для внешнего доступа нужен HTTPS.
На каждом авторизованном запросе выполняются поиск пользователя и bcrypt;
нет rate limiting и выравнивания времени отказа для неизвестного/неактивного
пользователя. Высокая нагрузка не проверялась. Логи намеренно сообщают операцию
без текста SQL-ошибки: это снижает риск утечки, но усложняет диагностику.

Миграции и seed рассчитаны на один экземпляр приложения, без блокировки
параллельного старта и автоматического rollback уже применённых версий.
При развитии сервиса полезны защита Auth от перебора, метрики и
нагрузочные проверки; для нескольких экземпляров — согласованный запуск
миграций, для реального просмотра — отдельный видеосервер/CDN и защита HLS URL.
