# IPTV backend

Мини-бэкенд IPTV на Go 1.26+ и PostgreSQL 17 по [ТЗ](docs/assignment.md). API возвращает список доступных каналов и HLS URL для просмотра. Реализованы бессрочные и временные подписки на отдельные каналы. Админ-панель и кэширование не реализованы.

## Запуск

Нужны Docker с Compose и свободный порт `8080`. Команды выполняются из корня проекта в Linux/WSL; Go на хосте для запуска не нужен.

```sh
docker compose --env-file .env.example up --build
```

После сообщения `HTTP server started` API доступен на `http://127.0.0.1:8080`. Схема и demo-данные создаются автоматически: два пользователя и пять каналов.

| Логин | Пароль | Состояние |
| --- | --- | --- |
| `viewer` | `viewer_demo` | Активен |
| `inactive` | `inactive_demo` | Выключен, получает `401` |

`.env.example` содержит публичные настройки для локальной проверки. Для своих настроек выполните `cp .env.example .env`, отредактируйте `.env` и используйте `docker compose up --build`. В остальных командах тоже убирайте `--env-file .env.example`.

Остановка: `docker compose --env-file .env.example down`. Логи: `docker compose --env-file .env.example logs -f app`.

Данные сохраняются в volume `postgres_data` после остановок и перезапусков. Seed не восстанавливает удалённые записи и не продлевает подписки. Для полного перезапуска используйте `down` и запуск заново: `up` ждёт готовности БД, а `restart` всего стека этого не гарантирует.

Чтобы начать с чистой БД, выполните команды ниже. `--volumes` удалит все данные БД этого Compose-проекта; при запуске снова появятся demo-данные.

```sh
docker compose --env-file .env.example down --volumes
docker compose --env-file .env.example up --build
```

## API

Оба ресурса требуют HTTP Basic Auth: пользователь должен быть активен и передать верный пароль. Примеры выполняются во втором терминале.

Список каналов:

```sh
curl -u viewer:viewer_demo http://127.0.0.1:8080/api/v1/channels
```

Ответ `200` на чистой БД в первые сутки после запуска:

```json
{
  "channels": [
    {"id": 1, "number": 1, "name": "Первый"},
    {"id": 2, "number": 2, "name": "Россия 1"}
  ]
}
```

В списке только активные каналы с действующей подпиской, без URL потоков. Сортировка — по `number`, затем `id`. Без подписок ответ — `{"channels":[]}`.

Ссылка на просмотр:

```sh
curl -u viewer:viewer_demo http://127.0.0.1:8080/api/v1/channels/1/playback
```

Ответ `200`:

```json
{
  "channel_id": 1,
  "url": "https://stream.example.com/live/ch1/index.m3u8"
}
```

URL берётся из БД. Demo-ссылки показывают формат HLS-плейлиста; видеосервера нет. ID — положительный десятичный `int64`, ведущие нули и `+` допустимы. Оба ресурса поддерживают `HEAD`: заголовки без тела ответа.

Ответы API используют `Content-Type: application/json`. Ошибки имеют единый формат:

```json
{"error":{"code":"unauthorized","message":"authentication required"}}
```

| Статус | `error.code` | Причина |
| --- | --- | --- |
| `400` | `invalid_id` | Неверный ID, ноль, отрицательное число или переполнение |
| `401` | `unauthorized` | Нет учётных данных, неверный пароль, неизвестный или выключенный пользователь |
| `403` | `subscription_required` | Активный канал без действующей подписки; URL не возвращается |
| `404` | `channel_not_found` | Канал не существует или выключен |
| `404` | `not_found` | Неизвестный путь |
| `405` | `method_not_allowed` | Неверный метод; `Allow: GET, HEAD` |
| `500` | `internal_error` | Внутренний сбой без SQL и других подробностей |

У `401` есть заголовок `WWW-Authenticate: Basic realm="iptv"`. В `/api/v1` и `/api/v1/…` аутентификация проверяется до маршрута, метода, ID и перенаправлений. Лишний завершающий `/` даёт `404` после аутентификации.

### Postman

Через Import в Postman Desktop откройте [коллекцию](docs/postman/iptv.postman_collection.json). В ней настроены Basic Auth, demo-значения и проверки ответов. Запросы можно отправлять через Send или запускать вместе через Run collection. Адрес `base_url`, `username` и `password` меняются во вкладке Variables.

Коллекция не меняет данные. Ожидаемые ответы рассчитаны на исходные demo-каналы и подписки. Если HTTP proxy мешает доступу к localhost, добавьте `127.0.0.1` в его исключения; для curl можно указать `--noproxy 127.0.0.1`.

## Подписки

Подписка — связь пользователя с каналом с полями `active` и `expires_at` (`timestamptz`). Прямая связь позволяет проверить доступ одним SQL-запросом. Пользователь, канал и подписка должны быть активны.

`NULL` в `expires_at` означает бессрочную подписку. Временная действует, пока `expires_at > statement_timestamp()`: срок проверяется по времени начала SQL-запроса в PostgreSQL, без фоновой задачи. В момент истечения доступ уже закрыт.

Включение истёкшей подписки без продления не возвращает доступ. Если срок истёк между получением каталога и playback, последний вернёт `403`.

На чистой БД у `viewer`:

| ID канала | Подписка | Каталог / playback |
| --- | --- | --- |
| `1` | Бессрочная | Есть / `200` |
| `2` | На сутки с первого seed | До истечения: есть / `200`; затем нет / `403` |
| `3` | Выключена | Нет / `403` |
| `4` | Уже истекла | Нет / `403` |
| `5` | Бессрочная, но канал выключен | Нет / `404` |

Управление подписками — через SQL. Откройте psql:

```sh
docker compose --env-file .env.example exec db sh -c 'exec psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Выдать `viewer` бессрочную подписку на канал 3 или заменить существующую:

```sql
INSERT INTO subscriptions (user_id, channel_id, active, expires_at)
SELECT id, 3, true, NULL FROM users WHERE login = 'viewer'
ON CONFLICT (user_id, channel_id)
DO UPDATE SET active = true, expires_at = NULL;
```

Выключить её, сохранив срок:

```sql
UPDATE subscriptions s
SET active = false
FROM users u
WHERE s.user_id = u.id AND u.login = 'viewer' AND s.channel_id = 3;
```

Для включения замените `false` на `true`. Сделать подписку временной или продлить на час:

```sql
UPDATE subscriptions s
SET active = true, expires_at = statement_timestamp() + interval '1 hour'
FROM users u
WHERE s.user_id = u.id AND u.login = 'viewer' AND s.channel_id = 3;
```

Вместо относительного срока можно указать `timestamptz '2030-01-01T00:00:00Z'`. Для бессрочного права используйте `expires_at = NULL`, для истечения сейчас — `expires_at = statement_timestamp()`. `UPDATE 0` означает, что подписки нет. Изменения видны со следующего запроса; выход из psql — Ctrl+D.

При обновлении с версии без подписок сохраните прежние Compose-проект, настройки и volume. Миграции и seed применятся при `up --build`; права получат сохранившиеся demo-записи `viewer` и каналов с исходными номером и URL. Остальным назначьте права вручную.

## Настройки

Compose читает `.env` или файл из `--env-file`; переменные окружения имеют приоритет.

| Переменная | Назначение / значение по умолчанию |
| --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Обязательные параметры БД в Compose |
| `DATABASE_URL` | Обязательный PostgreSQL DSN приложения |
| `HTTP_PORT` | Порт на хосте, `8080` |
| `HTTP_ADDR` | Адрес Go-процесса, `:8080`; в Compose задан явно |
| `DB_MAX_CONNS` | Максимум соединений pool, `10` |
| `LOG_LEVEL` | `debug`, `info`, `warn`, `error`; по умолчанию `info` |

В `DATABASE_URL` укажите те же пользователя, пароль и БД, что в `POSTGRES_*`; адрес БД внутри Compose — `db:5432`. Спецсимволы в логине и пароле URL экранируются через percent-encoding. `POSTGRES_*` применяются только к пустому volume: смена настроек не меняет пароль существующей БД.

Для запуска через `make run` нужны Go 1.26+, GNU Make и доступная БД. Настройки передаются через окружение: само приложение `.env` не читает.

## Проверки

Нужны Go 1.26+ и GNU Make:

```sh
make check
```

Команда проверяет форматирование, build, vet и unit-тесты без Docker и БД. Отдельно тесты — `go test ./...` или `make test`; остальные команды — `make help`.

Для integration-тестов нужны Docker и свободный порт `15432`. Они используют отдельную PostgreSQL 17 в tmpfs и создают свою schema для каждого теста. Не указывайте demo-БД в `TEST_DATABASE_URL`.

```sh
(
  set -e
  . ./.env.example
  export TEST_DATABASE_URL
  trap 'docker compose --env-file .env.example -f compose.test.yaml -p iptv-test down' EXIT
  docker compose --env-file .env.example -f compose.test.yaml -p iptv-test up -d --wait db
  make integration
)
```

Стенд остановится и при ошибке. Проверяются Auth, API, миграции/seed, подписки, истечение срока и отмена запросов. GitHub Actions запускает те же `make check` и `make integration` для PR в `main` и push в `main`.

## Решения и ограничения

Для двух ресурсов хватает stdlib. HTTP, сценарии и SQL разделены между `internal/httpapi`, `internal/iptv` и `internal/postgres`. Интерфейсы у потребителей позволяют тестировать обработчики и сценарии без БД.

PostgreSQL выбрана для работы с несколькими соединениями и одновременных запросов. `github.com/jackc/pgx/v5/pgxpool` даёт драйвер и pool. SQL написан явно, пользовательский ввод передаётся параметрами. БД запускается отдельным сервисом через Compose.

Пароли хранятся как bcrypt-хэши со случайной солью. Для этого используется `golang.org/x/crypto/bcrypt`: готовой реализации в stdlib нет. Bcrypt требует много вычислений на каждую попытку, затрудняя перебор при утечке хэшей. Cost — 10, пароли длиннее 72 байт отклоняются без усечения. Остальные внешние модули — зависимости pgx.

Миграции встроены в бинарник, seed выполняется один раз: для подготовки БД не нужна отдельная команда. Каждый этап транзакционный; ошибка останавливает запуск. Решение рассчитано на один экземпляр приложения, без координации параллельного старта.

Basic Auth задан в ТЗ; пароль и права проверяются при каждом запросе. Без кэша изменения видны сразу, но каждый запрос расходует CPU на bcrypt и обращается к БД. Высокая нагрузка не проверялась.

Образ — статический бинарник в `scratch`, запуск без root. HTTP открыт только на локальном адресе; для внешнего доступа нужен HTTPS. API защищает выдачу URL, а доступ к самому потоку должен проверять видеосервер.

По SIGTERM запросам даётся 10 секунд, затем они отменяются и ресурсы закрываются; Compose ждёт 15 секунд. HTTP-таймауты: заголовки — 5 с, чтение/запись — 10 с; SQL — 3 с. Открытое соединение ждёт следующий запрос 60 секунд, затем закрывается (idle timeout).

Логи пишутся в stderr в формате JSON: метод, путь, статус и длительность запроса. Пароли и текст SQL-ошибок не выводятся, поэтому диагностика сбоев БД требует отдельной проверки.

Дальше я бы ограничил попытки входа и проверил сервис под нагрузкой, прежде чем добавлять кэш. Для нескольких экземпляров понадобится согласовать запуск миграций, для реального просмотра — подключить видеосервер с проверкой доступа.
